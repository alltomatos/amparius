# Contrato i18n v1 — Internacionalização

Versão 1 · 28/11/2026 · Ver ADR 0049.

Decisões do Ronaldo já incorporadas: espanhol é `es-419` (neutro
latino-americano); `pt-PT` é só idioma de interface — sem moeda, sem
fiscalidade portuguesa, sem documento fiscal fora de `pt-BR`.

## 1. Locales suportados

| Locale | Papel |
|---|---|
| `pt-BR` | Padrão do sistema e fallback final |
| `pt-PT` | Idioma de interface; mesma moeda/fiscal do registro |
| `es-419` | Espanhol neutro latino-americano; mesma moeda/fiscal do registro |

Fallback: `pt-PT → pt-BR`, `es-419 → pt-BR`. Nenhum locale cai em outro que
não seja `pt-BR`.

## 2. Resolução de locale

Ordem, do mais específico ao menos específico:

1. `identity.app_user.locale` (usuário autenticado).
2. `identity.company.locale` (padrão da empresa; usado também em link de
   convite/onboarding com `company_id` conhecido antes do login).
3. Cabeçalho `Accept-Language`, só nas telas de login/onboarding, só como
   sugestão inicial de locale — nunca persiste, nunca decide locale de
   e-mail ou documento já gerado.
4. `pt-BR`.

O locale resolvido entra no contexto de requisição (`ctx.Locale`) pelo
mesmo middleware que já resolve `tenant_id`; handlers não leem
`Accept-Language` nem fazem fallback próprio.

### Colunas novas (fatia I18N-01B)

```sql
ALTER TABLE identity.app_user
  ADD COLUMN locale text NOT NULL DEFAULT 'pt-BR'
    CHECK (locale IN ('pt-BR', 'pt-PT', 'es-419'));

ALTER TABLE identity.company
  ADD COLUMN locale text NOT NULL DEFAULT 'pt-BR'
    CHECK (locale IN ('pt-BR', 'pt-PT', 'es-419'));
```

Migration forward-only; sem impacto em RLS (coluna de metadado de
interface, não cruza tenant).

## 3. Chaves de tradução

- Formato: `modulo.tela.elemento` (snake_case por segmento), nunca o
  texto-fonte.
- Exemplos: `finance.cash_session.open_button`,
  `errors.AUTH.INVALID_CREDENTIALS`, `auth.login.submit_button`.
- Namespace `errors.<CODE>` espelha o código estável de erro já usado nos
  contratos HTTP existentes (ex. `docs/contracts/auth-login-v1.md`); o
  `code` da resposta não muda, só ganha um `message` localizado ao lado.

## 4. Backend Go — formato de erro

```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "E-mail ou senha incorretos.",
  "locale": "pt-BR"
}
```

- `code` é a chave de decisão de qualquer cliente; `message` é só exibição,
  já traduzido no locale resolvido da requisição.
- Catálogo do backend em `locales/<locale>/errors.json`, carregado em
  memória no boot (`internal/platform/i18n`); nenhuma tradução é buscada em
  runtime.
- Nenhum texto traduzido é escrito em dado de negócio (nome de produto,
  descrição de contrato, observação de atendimento) — esses campos
  permanecem exatamente como o usuário digitou.

## 5. Clientes (web, manager, desktop)

- Catálogo: JSON por locale, sintaxe ICU MessageFormat.

```json
{
  "finance.cash_session.closed_diff": "{count, plural, one {# diferença encontrada} other {# diferenças encontradas}}"
}
```

- Formatação de data/número usa `Intl` (web/manager) ou `icu4x`/equivalente
  (desktop Rust); nunca concatenação manual de string.
- **Moeda nunca deriva do locale.** O campo de moeda vem do registro
  financeiro (`BRL`, e futuramente `EUR` se e quando houver operação em
  moeda europeia); o locale só formata separador decimal, agrupamento e
  posição do símbolo.

  Exemplo de contrato (não é cálculo, é só exibição):
  `{"amount_cents": 150000, "currency": "BRL"}` exibido em `pt-PT` mostra
  `1.500,00 R$`/`R$ 1.500,00` conforme convenção de formatação do locale —
  nunca `€`, porque a moeda do registro continua `BRL`.
- Assistente de IA: `locale` do envelope de contexto
  (`docs/design/AI-ASSISTANT.md` §2) segue a mesma resolução da seção 2
  deste contrato; catálogo de `intents`/`suggestions` é traduzido como
  qualquer outra chave de UI.

## 6. Fronteira com o fiscal

- NFS-e, NF-e, DANFE, DPS e XML oficiais permanecem **inteiramente em
  `pt-BR`**, incluindo a representação visual do documento. Isso é
  obrigação legal (AGENTS.md §2.1/§6, ADR 0010, ADR 0031), não uma opção de
  configuração.
- A tela em torno do documento fiscal (botões, status, erro de emissão) é
  traduzida normalmente; o documento em si nunca.
- Termo fiscal fora do XML (ex. rótulo "ISS" num resumo): tratamento
  definido pela Lacuna 1 do ADR 0049 (ainda em aberto).

## 7. Conteúdo cadastrado pelo usuário

| Conteúdo | Tratamento |
|---|---|
| Catálogo de produtos/serviços do tenant | Não traduzido automaticamente; locale(s) do próprio tenant |
| Ajuda contextual / Userguide | Catálogo de chaves (seção 3), fallback `pt-BR` |
| System prompt do assistente de IA | Varia por locale resolvido (seção 2); conteúdo do tenant lido pelo prompt nunca é traduzido |

## 8. Offline / relay

- Catálogo (JSON ICU) é empacotado no binário do cliente e do relay;
  nenhuma busca de tradução em runtime (AGENTS.md §2.4).
- Catálogo tem `catalog_version` (semver) independente da versão do
  binário; o relay valida compatibilidade no startup.
- O snapshot assinado do relay (ADR 0022; ADR 0046, número a confirmar no merge) carrega só dado
  estruturado (códigos, ids, valores) — nunca texto traduzido. Tradução
  acontece inteiramente no cliente a partir do catálogo local.

### Critério de teste (fatia I18N-01D)

1. Com o relay desconectado de rede, trocar o locale ativo e confirmar que
   toda string visível vem do catálogo local (nenhuma chamada de rede
   disparada).
2. Inspecionar o payload do snapshot assinado e confirmar ausência de
   qualquer string de catálogo de UI (só código/id/valor).

## 9. Testes de contrato mínimos

1. **Cobertura de chaves (CI, todas as fatias)**: para cada locale
   não-`pt-BR`, toda chave presente no catálogo `pt-BR` existe no catálogo
   do locale ou cai em fallback documentado; falha o build se faltar chave
   usada por uma tela/erro ativo. Chave extra no locale não-padrão é só
   aviso.
2. **Moeda não deriva do locale**: registro com `currency: "BRL"` exibido
   em `pt-BR`, `pt-PT` e `es-419` resulta no mesmo valor e mesma moeda,
   variando apenas o separador/posição do símbolo — nunca aparece `€` para
   um registro `BRL`.
3. **Fiscal intocado**: golden file de DPS/NFS-e gerado com usuário em
   `pt-PT` ou `es-419` produz XML byte-a-byte idêntico ao gerado com usuário
   em `pt-BR` (exceto, se aplicável, metadado de auditoria que não faz
   parte do leiaute oficial).
4. **Offline sem rede**: critério da seção 8.

## 10. Fatias e critérios de aceite

| Fatia | Entrega | Critério de aceite |
|---|---|---|
| I18N-01B (backend Go) | Catálogo de erros, middleware de locale, colunas `locale`, teste de cobertura de chaves no backend | Item 1 e 3 (parcial: erro localizado) deste contrato |
| I18N-01C (web + manager) | Catálogo ICU, seletor de locale, formatação `Intl`, teste de cobertura de chaves no frontend | Item 1 e 2 |
| I18N-01D (desktop Rust) | Catálogo empacotado + versão, formatação ICU, teste de cobertura de chaves, prova offline | Item 1, 2 e 4 |
| I18N-01E (documentação/Userguide) | Glossário publicado, processo de revisão nativa, primeira leva de páginas traduzidas | Glossário revisado por falante nativo antes de publicar (ADR 0049 §8) |

## 11. Lacunas e decisões abertas

Ver ADR 0049, seção "Lacunas e decisões abertas" — lista única, 4 itens em
aberto (glossário de termo fiscal fora do XML; catálogo multilíngue de
produto do tenant; formato de documento/telefone por país; fuso horário por
locale). As duas pendências originais sobre espanhol e sobre
moeda/fiscalidade de `pt-PT` já foram decididas pelo Ronaldo e não aparecem
mais aqui.
